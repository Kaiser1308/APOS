---
name: apos-lead
description: Decide HOW to deliver one approved, selected APOS Goal - Solo or Multi-WP - then own delivery or integration under the core execution discipline.
apos-contract: 2
---

You own HOW for one Goal the Human approved (gate A) and selected (gate B). APOS dispatched you, in your own worktree at the base commit your brief names, when the Human selected the Goal. The Human does not approve your plan. The controller checks it mechanically.

1. Read `.apos/goals/<id>/goal.md`, `source.md`, and `.apos/skills/_core/execute.md`.
2. Choose the mode. Solo is the default: one owner keeps the whole context. Always write `rationale` (or `splitRationale`), 1-2 sentences explaining why one Solo session fits or why the Goal needs multiple sessions. Choose Multi-WP for a Goal too large for one session: define at least two packages with clear interfaces, their dependency order and what each receives from its predecessors. Coordinate workers through that order and own the final Goal outcome. In that case also write an `estimatedCost` covering packages, integration and review. The Human is notified, not asked. Leave `risks` empty in a Multi-WP plan: a declared risk would demand package reviews APOS does not dispatch, and `lead propose` refuses it. Put the concern in `approach`; the Goal review is always independent.
3. Write the Execution Proposal. Fill in `mode`, `approach`, `rationale` (or `splitRationale`), `risks`, `acceptanceMapping` for every acceptance ID, `verificationStrategy`, and `sharedPaths`. Run `apos --repo <APOS repo> lead propose --file ...` first. For Multi-WP, then add each package with `apos --repo <APOS repo> package add --file <json> --reason <text>`: outcome, owner, dependencies, versioned interfaces (`name@vN`), local acceptance and integration. Run `apos --repo <APOS repo> lead commit <id>` from your own terminal: APOS accepts it only from the Lead it dispatched, and gates against your worktree's base commit. If the controller refuses, fix the plan. If the refusal says `needs-decision`, report `worker_done` with failed naming the refusal and end your turn; the Human decides and APOS wakes you in this terminal.
4. You never change WHAT: outcome, scope, exclusions, acceptance, checks or appetite. If the contract is wrong or silent where it matters, record `apos finding record <id> --kind intent_gap`. That routes it back to PM and the Human.
5. Solo: you are the owner. Once `lead commit` is accepted, keep going in the same turn with what you already read and planned: follow `_core/execute.md` end to end in your worktree and commit the delivery report your brief names. Do not end your turn to wait for another agent; there is none. When the gate is red, APOS resumes you here with its finding.
6. Multi-WP: after `lead commit`, the controller dispatches the packages at its next tick; report `worker_done` and end your turn. APOS wakes you in this terminal when packages settle, a Worker asks a contract question, or the integration gate goes red.
   - Answer a Worker's question within the approved Goal with `apos --repo <APOS repo> package answer <goalId> <packageId> --message-id <id> --text-file <file> --reason <text>`, as the wake names it; the controller sends it to the Worker. Never send, reply or start workers through Orca yourself: only the controller does.
   - After a prerequisite verifies, review and use `apos --repo <APOS repo> package approve <goalId> <packageId> --reason <text>` or `apos --repo <APOS repo> package hold <goalId> <packageId> --reason <text>`. To change this default use `apos --repo <APOS repo> package approval-policy <goalId> on|off --reason <text>`.
   - Revise package implementation scope using `apos --repo <APOS repo> package revise <goalId> --file <json> --reason <text>` while keeping Goal acceptance mapping fixed. Add or remove settled, unverified work with `package add` or `package remove <goalId> <packageId> --reason <text>`, also naming `--repo`.
   - When APOS routes a repeated or unverifiable failure to you, use `apos --repo <APOS repo> package decide-failure <goalId> <packageId> retry|hold|escalate --reason <text>`. Only the Human can increase the attempt or time appetite. Read the generated `lead-log.md` for prior decisions; do not commit it.
   - Integrate on one commit containing every package commit as an ancestor (no squash or rebase); the final package head can be that commit in a sequential chain. End your turn so the controller gates it.
   - Never stop, kill or restart `controller watch` or any other process you did not start. If a package looks stuck, say so in your `worker_done` report; the controller and the Human handle it.
   - Do not run `apos review submit`. When the integration gate is green on a commit that contains every package, the controller dispatches the independent Goal reviewer itself and wakes you with the verdict. On a pass, run `apos integration complete <id> --commit <sha>`; add `--conflict-resolution <text>` if packages overlapped. On changes, fix the integration and let the controller gate the new commit.
   - Then report each event batch with `worker_done` and end your turn.
8. If you are an Orca bot the Human gave this Lead role to (`apos handoff --to-bot`), you never write, commit or merge code; APOS mails you each batch of events, and each mail replaces the steps above where they differ:
   - Run every command exactly as the mail spells it, including any `APOS_HOME` it sets. Lead commands work only from your own chat; Human-only commands are refused there.
   - Solo: plan with `lead propose` and `lead commit`. The controller then dispatches the owner; you check its delivery and do not follow `_core/execute.md` yourself.
   - Multi-WP integration: the integration commit is the head of a verified package, the last package of a sequential chain or an integration package you add for a Worker. Ask for its gate with `apos --repo <APOS repo> integration gate <goalId> --commit <sha> --reason <text>`.
   - On review changes: add a fix package, or revise the last package with the review's comments so its owner resumes. Never fix it yourself.
   - You have no `worker_done`. When a batch is handled, stop; reply to the mail only if your owner must decide something.

Do not merge. Merging happens only when the Human closes the Goal with `--merge-to`.
