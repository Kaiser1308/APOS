# Assurance benchmark

This benchmark measures APOS on a controlled corpus and remains separate from the tests of APOS itself. The first reported aggregate has been withdrawn because its Node dependencies were not installed from the case lockfiles.

The intended input is a controlled directory outside Git repositories containing `manifest.json`, Git bundles, Goal documents and plans. The runner rejects corpus and output paths inside a detectable Git repository or worktree; this check cannot establish whether other storage is private or durable. The manifest fixes each delivery commit and states the independent oracle before any gate is run. It is sensitive: do not commit it, its bundles, detailed results, or holdout cases to a public repository. Retain the original manifest, bundles and supporting files, their digests, the detailed output and the exact APOS commit in controlled storage; access and backups must be arranged by the corpus owner. A path on one machine alone is not a durable archive.

Benchmark execution currently requires Linux: it depends on POSIX executable wrappers, permissions and GNU `/usr/bin/time`, and rejects other platforms before creating output. Windows CI exercises platform-independent contracts but does not establish Windows benchmark support. Install the pinned Node dependencies with `npm ci`; Git, GNU `/usr/bin/time` and the tools named by the corpus setups are also required. Python examples need Python and pytest, and a setup that calls `python` needs that command available even on a machine that normally calls it `python3`. Run `npm run bench -- /private/corpus /private/new-output`; the output directory must not already exist. Run it without another build or test writing to `dist` in the same checkout; overlapping builds can corrupt an in-flight process's module load. The runner makes isolated repositories and APOS homes, invokes APOS for the preparation actions and `package submit --json`, and writes detailed JSON and CSV under the output directory. It runs twice and reports disagreements. Setup actions and the repositories they test execute code: run only trusted corpora in an appropriately isolated environment. Do not use this runner as a sandbox for an untrusted holdout.

Each Node snapshot must contain a valid npm v2-or-newer lockfile and no committed `node_modules`. Before APOS runs, the runner installs each referenced snapshot into a separate seed checkout with a case-local npm cache; failure stops the case without a verdict. Seeding may fetch lockfile-pinned packages and honors an explicit offline setting; APOS worktrees then install from the case lockfile and isolated cache in offline mode. Inherited dependency directories, `NODE_PATH` and `NODE_OPTIONS` are removed, while `npx` and `npm exec` are restricted to executable names installed inside the case worktree. The `npm` guard permits `ci`, `run`, `test` and version queries, and rejects dynamic installs; setups needing other npm commands must be adapted explicitly. Lockfile local links must stay inside the snapshot. Installation scripts execute as the current user during seeding, and these guards are not an OS security sandbox.

`evidenceDigest` contains the digests APOS reports for tool logs plus the SHA-256 of the captured gate output. The latter is also recorded separately as `resultDigest`: it preserves the controller's result and reasons when a structural check produces no tool log. The output file is evidence of what APOS reported; it does not independently establish whether the code or a test was correct.

The manifest format is version 1: `cases` contains unique `id`, `goalKind`, `family`, `severity`, `truth` (`fault`, `clean`, or `limitation`), `expected`, relative `repository` (a Git bundle), full `deliveryCommit`, an independently justified `oracle`, `actions` (APOS argument arrays), `goalId`, and `packageId`. A case can pin `clock` to an ISO UTC timestamp for APOS deadline logic. List fixed commits referenced only inside other files, such as a plan's base, in `dependencyCommits` so their dependencies are seeded too. The tokens `{corpus}`, `{repo}`, and `{delivery}` in actions expand to paths or the commit. An action `['@checkout', '<full commit>']` switches the isolated repository to a fixed snapshot between APOS actions. The bundle HEAD must be the intended starting snapshot and contain every commit referenced by the actions. An oracle is a statement of truth, not the APOS result; the schema cannot independently verify its validity.

False-green uses all fault cases as its denominator; false-red uses all clean cases. `unverifiable` and `needs-human` are counted separately, never as a detection or false-red. Known limitations are excluded from those two populations and counted separately. Detection by family counts red verdicts among fault cases. Costs cover the measured package submission, including child processes, using GNU `time`: `duration` is wall time in milliseconds, `cpu` is user plus system CPU seconds, and peak RSS is that of an individual process in the measured process tree, not a simultaneous process-tree memory peak. `gateCommands` counts gate-bearing CLI commands, including preparation, rather than internal gate attempts. Results do not include setup cost; concurrent activity, caching and the operating system affect measurements. `caughtBy` lists the failing check IDs reported in APOS's reasons; a failing check does not establish which fault caused it, and the value is null when those IDs are unavailable.

A holdout contributor can supply a sealed corpus through a private channel to an operator, who verifies provenance, oracle, executable contents, and access before running it separately. Keep holdout cases apart from cases used to develop or tune the benchmark. No such intake service, automated isolation, or durable private storage is supplied here. Review any aggregate report for case leakage before publishing it.

## Withdrawn preliminary aggregate

The aggregate previously reported for commit `7cf5220853075993fcff25bbb639ea37a6f863c9` must not be used. The runner linked the APOS checkout's `node_modules` into cases, including cases whose lockfiles did not specify those dependencies; a case could also modify that shared tree. The original private corpus and detailed results are retained for audit. A replacement aggregate requires corrected fixed snapshots and fresh runs.

## First isolated aggregate

A curated private development corpus contained 28 cases derived from the seven demos, covering five Goal kinds and eight fault families. The manifest stated the oracle before the run; an audit compared its fixed snapshots and oracle metadata with the prior corpus, with Node lockfiles corrected for isolated installation. Some oracles also have independent behavioral or source checks. The recorded file times and retained audit are local evidence, not an independently timestamped or externally reviewed oracle certification. This is a small selected sample, not an independent holdout or an estimate for a wider population.

The two sequential repetitions ran on clean APOS commit `6c88d1ba584e33d85fcc332d43b4450edb6ba231`. The subsequent Linux platform guard does not change the measured Linux execution path. Every case produced the same verdict in both repetitions and generated plans matched; the frozen corpus and manifest digests match the retained inputs, and all 56 recorded evidence digests match retained files. Twelve submissions did not provide a tool-log digest; their captured controller result is retained instead.

| Metric | Repetition 1 | Repetition 2 |
| --- | ---: | ---: |
| False-green, fault cases | 6/18 (33.3%) | 6/18 (33.3%) |
| False-red, clean cases | 2/9 (22.2%) | 2/9 (22.2%) |
| Unverifiable, all cases | 0/28 | 0/28 |
| Needs-human, all cases | 1/28 (3.6%) | 1/28 (3.6%) |
| Known limitations, reported separately | 1 | 1 |

Abstentions are included in the population denominators but are not counted as detections or false-reds. A red verdict on a faulty case indicates a block; it does not establish that APOS identified the fault, or distinguish correct code from an incorrect test. Family-level results remain private because the groups are small. Evidence shows what the gate reported, not ground truth.

The run used Linux x64 kernel `7.0.0-44-generic`, an AMD Ryzen 7 4800H, Node `v22.22.1`, npm `9.2.0`, Python `3.14.4`, pytest `9.0.2`, Git `2.53.0`, and GNU `time`. Gate wall times summed to 508.9 s and 506.2 s; user plus system CPU summed to 644.9 s and 639.7 s. Maximum reported individual-process RSS was 237,800 KiB and 236,296 KiB. Total elapsed time was approximately 39.7 minutes including preparation; per-case gate costs exclude setup. This was a shared machine, so scheduling, other activity and caches introduce noise; no random seed was controlled, and two repetitions do not provide a confidence interval. No LLM reviewer was used. The private corpus and detailed results are retained locally, but no independent holdout or backup has been verified.
