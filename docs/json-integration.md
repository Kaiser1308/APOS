# APOS JSON integration v1

The schemas are [result-v1](../schemas/result-v1.schema.json) and [events-v1](../schemas/events-v1.schema.json). The `schemaVersion` is the number `1`. Consumers should ignore additional properties and check the version before interpreting a response. `package submit`, `integration gate`, `outcome close`, `goal show`, `inbox` and `tests submit` accept `--json`. Normal text output is unchanged. Existing `package submit --json` and `inbox --json` retain their previous fields and add the common fields; consumers that reject unknown properties must update their parser.

For a gate, `verdict` is the recorded gate result; pending maps to `unverifiable`. Test submission reports whether its test lock was accepted, not whether the delivery passed. Goal show reports the last recorded delivery gate, or `unverifiable` when absent. Inbox has no gate verdict and reports `unverifiable`; its `items` and `cursor` retain their existing meaning. A successful close without a close-stage report is `unverifiable` even though `status` is `closed`. `null` means unavailable or not established; `findings: []` does not prove no findings because individual finding details are not exposed here, as stated in `assuranceLimitations`. `evidence` includes available check-log SHA-256 digests, not a claim that the artifacts were independently verified. `caughtBy` and retryability are not determined. A `requiresHuman: true` comes from a `needs-human` verdict; null means unknown.

Gate commands use exit 0 for green, 1 for red, and 3 for unverifiable or needs-human. A successful test lock exits 0, refusal 1. JSON close exits 3 if no close-stage report was available even when closing succeeded. JSON Goal and inbox reads also use the 0/1/3 mapping; inbox has no gate verdict and exits 3 on a successful JSON read. This changes the previous `inbox --json` success code from 0 to 3, so callers must update their handling. Inbox wait timeout remains 2. Input, precondition and unexpected errors print diagnostics to stderr and exit 1; they are not verdicts and do not necessarily produce JSON. `package submit` retains its prior JSON fields alongside the v1 envelope.

## Events and checkpoints

An index must be initialized explicitly once: `apos events --since 0 --json --initialize`. Save the returned `generation`, last event `seq` (or 0 when empty), and `anchor` together, transactionally with processing results. Resume with `apos events --since <seq> --generation <generation> --anchor <anchor> --json`. Process by event `id` idempotently: a consumer can crash after processing and before saving its checkpoint. When a response is empty, retain the returned generation, anchor and previous sequence. The anchor is the hash at the returned high-water mark. `--since 0 --json` reads an existing index from the beginning.

The stream combines the project and per-Goal journals under the journal lock. It indexes events discovered in sorted journal filename order, in each journal's own order. This is a deterministic discovery order, not proof of historical occurrence order across journals; this applies to events discovered together at any time. Journal writes that completed before a crash but have not yet been indexed are reconciled on the next read. Index writes are fsynced before output. A torn or corrupt index, source mismatch, missing index, wrong generation or mismatched cursor is an error; APOS does not silently recreate the index. An explicit initialization after loss starts a different generation: consumers must reset and replay, deduplicating by event ID. Preserve `stream.jsonl` together with all journals in backups, under the same lock.

The consumer must persist and supply both the generation and anchor corresponding to its greatest processed sequence. They detect an incompatible index, including a rollback that removes or changes that checkpoint. No local algorithm can identify a coordinated rollback of both APOS state and a consumer checkpoint, or determine that an event existed after an older checkpoint if both were restored together. Do not claim exactly-once delivery; coordinate backup/restore and use stable IDs for deduplication. A torn index requires restoring a consistent backup or deliberately resetting the index and every consumer. Errors do not mutate a corrupt index for repair.
