# APOS v3 – Đợt 2: Định dạng kết quả, danh mục, setup v2 – Kế hoạch

> **Cho worker:** làm theo từng task, TDD. Nhánh từ `main` *sau khi PR đợt 1 đã merge*. Commit đầu tiên chép file này vào `docs/superpowers/plans/2026-11-22-apos-v3-dot2.md`. Nếu kế hoạch sai ở chỗ đổi hành vi thì hỏi Lead, không tự đổi phạm vi.

**Goal:** APOS đọc được kết quả của mọi công cụ qua bốn định dạng chuẩn. Có danh mục công cụ cho Python, Java và TypeScript. Mỗi dự án có bộ setup v2: Lead viết nháp, APOS chạy thử, anh duyệt, khoá, và mỗi Goal ghim một phiên bản setup.

**Architecture:**
- Bộ đọc kết quả là hàm thuần trong `src/domain/results/`.
- Danh mục là các file YAML đóng gói trong `catalog/`, có thể ghi đè ở `~/.apos/catalog/`.
- Setup v2 có schema zod trong `src/domain/project-setup.ts`.
- Lịch sử setup (đã chạy thử, đã duyệt) nằm trong một luồng log mới ở cấp dự án: `events/_project.jsonl`, nối hash như log của Goal.
- Gate chưa chạy theo lớp. Việc đó là đợt 4. Đợt này chỉ cho check dạng lệnh đọc lỗi từ báo cáo chuẩn, thay cho regex `failurePattern`.

**Tech Stack:** TypeScript, zod, commander, vitest; thêm `yaml` và `fast-xml-parser` **chỉ khi anh đã đồng ý** (câu hỏi trên item 5). Nếu anh không đồng ý: setup là `.apos/project.json`, danh mục là `.json`, JUnit đọc bằng bộ đọc tối giản tự viết. Bộ đọc tối giản phải qua mọi test của Task 1, kể cả CDATA và entity.

**Spec:** `docs/superpowers/specs/2026-11-22-apos-v3-design.md`, mục 6.2, 6.6, 6.7, 7.1, 10 (đợt 2).

## Global Constraints

- Lõi không biết tên công cụ hay ngôn ngữ nào. Mọi tên công cụ chỉ nằm trong `catalog/`.
- Danh mục không có giá trị bảo đảm. Chỉ setup đã có probe đạt và đã được anh duyệt mới được gate dùng.
- Bản nháp setup bật sẵn **sàn chặt** (spec 7.1): mẫu cấm theo stack, `mutation.minScore: 70` khi Goal gắn cờ.
- `schemaVersion: 1` (repo cũ) vẫn chạy: coi như "chưa có setup". Mọi bảo đảm theo setup tắt, check trong Goal vẫn chạy như cũ.
- `apos setup approve` là lệnh Human, dùng `confirmHuman` của đợt 1.
- `npm run check` xanh ở cuối mỗi task.

## Review Focus

1. **JUnit thật từ nhiều runner** (vitest, jest-junit, pytest `--junitxml`, Gradle, Maven Surefire): cùng một test phải ra cùng id giữa các lần chạy. `<error>` khác `<failure>`. Testcase không có `classname` vẫn có id.
2. **Báo cáo thiếu, rỗng hoặc XML hỏng:** kết quả là `unverifiable` với lý do rõ, không ném lỗi làm sập lệnh, không bị coi là "0 test, xanh".
3. **Setup bị sửa sau khi probe:** sha256 khác thì `approve` bị từ chối.
4. **`runOne` chạy ra nhiều hơn một test, hoặc không ra test nào:** probe trượt, chỉ rõ test nào.
5. **Repo nhiều phần, một phần không nhận ra được stack:** bản nháp vẫn tạo được, phần đó để trống và ghi chú "chưa nhận ra stack", không đoán bừa.

### Task 1: Bộ đọc kết quả

**Files:**
- Create: `src/domain/results/types.ts`, `junit.ts`, `sarif.ts`, `metric.ts`, `apos-json.ts`, `index.ts`, kèm test và fixture `src/domain/results/fixtures/` (JUnit từ vitest, jest-junit, pytest, Gradle, Surefire; SARIF từ eslint và semgrep; một file hỏng mỗi loại)

**Interfaces:**
- Produces:
  ```ts
  type ResultFormat = 'junit' | 'sarif' | 'metric' | 'apos-json';
  type TestOutcome = { id: string; status: 'pass' | 'fail' | 'error' | 'skip'; message?: string };
  type Finding = { ruleId: string; level: 'error' | 'warning' | 'note'; file?: string; line?: number };
  type ParsedReport =
    | { kind: 'tests'; tests: TestOutcome[] }
    | { kind: 'findings'; findings: Finding[] }
    | { kind: 'metric'; name: string; value: number }
    | { kind: 'unreadable'; reason: string };
  function readReport(format: ResultFormat, content: string, opts?: { metric?: string }): ParsedReport;
  ```
- id của JUnit: `${classname}::${name}`; thiếu `classname` thì dùng `${file ?? suite}::${name}`.
- `metric`: nội dung là JSON, lấy giá trị số theo đường dẫn chấm `opts.metric` (ví dụ `metrics.mutationScore`). Nội dung chỉ có một con số thì dùng thẳng.
- `apos-json`: `{"tests":[{id,status,message?}]}` hoặc `{"findings":[...]}`.

- [ ] Test cho mỗi fixture: số test, id, trạng thái; file hỏng ra `unreadable` (Review Focus 1, 2).

### Task 4: Schema setup v2 và luồng log cấp dự án

**Files:**
- Create: `src/domain/project-setup.ts`, `src/store/project-log.ts`, kèm test
- Modify: `src/app/init-project.ts` (bản mới ghi `schemaVersion: 2` với `parts: {}`), `src/store/journal.ts` (đọc thêm luồng `_project`)

**Interfaces:**
- Produces:
  ```ts
  type LayerSpec = CatalogTool & { when?: string };   // when: 'always' | 'flag:<name>'
  type PartSetup = { root: string; stack?: string; layers: Partial<Record<LayerId, LayerSpec[]>>; needsHuman: string[]; forbid: string[]; note?: string };
  type ProjectSetup = {
    schemaVersion: 2;
    parts: Record<string, PartSetup>;
    system?: Partial<Record<LayerId, LayerSpec[]>>;
    floor?: Partial<Record<'submit'|'integrate'|'close', LayerId[]>>;
    triggers?: { when: { changed?: string[]; goalFlag?: string }; at: 'submit'|'integrate'|'close'; run: string[] }[];
    mutation?: { minScore: number };
  };
  type LayerId = 'L0'|'L1'|'L2'|'L3'|'L4'|'L5'|'L6';
  function parseProjectSetup(text: string): { version: 1 } | { version: 2; setup: ProjectSetup; sha256: string };
  ```
- `sha256` tính trên nội dung đã chuẩn hoá xuống dòng.
- Luồng log `events/_project.jsonl` có sự kiện `setup-probed { sha256, commit, ok, results }` và `setup-approved { version, sha256, commit, confirmation }`. `version` tăng dần từ 1.

### Task 6: `apos setup probe` và `apos setup approve`

**Files:**
- Create: `src/app/setup-probe.ts`, kèm test
- Modify: `src/cli/commands/setup.ts`

**Interfaces:**
- `probeSetup(repo: string, commit: string): Promise<{ sha256: string; ok: boolean; results: ProbeResult[] }>`, với `ProbeResult = { part: string; layer: LayerId; tool: string; ok: boolean; reason: string }`.
- Probe đọc `project.yaml` **tại `commit`** và chạy trong worktree sạch (dùng lại `GitWorktreeFactory` và `ShellExecutor`).
- Luật cho từng công cụ:
  - Lệnh chạy được: không phải "command not found", không timeout.
  - Có `format` thì báo cáo không được `unreadable`; với `junit` phải có ít nhất 1 test.
  - Có `runOne` thì chạy với id đầu tiên của lần chạy đầy đủ, và phải ra đúng 1 test cùng id (Review Focus 4).
  - L1 và L2 chạy 2 lần, tập id và trạng thái phải giống nhau.
- Ghi `setup-probed`.
- `apos setup approve --commit <sha> [--on-behalf <text>]` (Human): cần một `setup-probed` có `ok` cùng `sha256` với file tại commit đó, nếu không thì từ chối (Review Focus 3). Duyệt thì ghi `setup-approved`.
- `apos setup show` in phiên bản đã duyệt mới nhất cùng sha256.

- [ ] Test: probe đạt và trượt (runOne ra 2 test, báo cáo hỏng, chạy 2 lần lệch nhau); approve khi sha256 khớp và khi lệch; approve không có TTY và không có `--on-behalf` thì bị từ chối.
- [ ] Viết.
- [ ] `npm run check` → commit.
